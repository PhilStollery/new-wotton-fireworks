WHAT V9 FIXES
--------------
Testing on Tito's own event page confirmed that valid mixed Wave One / Wave Two orders work correctly. The mixed-wave faults seen on the website were therefore introduced by our integration layer, not by Tito ticket settings.

V9 deliberately makes the website guard less invasive:

- All test price-band releases are mounted into one Tito widget once.
- Wave Two is only hidden/revealed visually. The Tito widget is never rebuilt when the next price becomes available.
- The website never writes ticket quantities back into Tito and no longer adds its own per-ticket `max` values.
- The website no longer changes Tito's native disabled state on Continue or on +/- controls. If a price-band total exceeds the remaining Activity allocation, it intercepts Continue and shows the clearer Wotton warning instead.
- Release rows are mapped primarily from Tito's release identity exposed in the inline HTML, with title/position fallbacks only if necessary. The availability API now also exposes the non-secret release ID for this mapping.
- Tito remains the final capacity authority. If two customers race for the last tickets, Tito's own Activity capacity still prevents overselling.

There is NO Adult/Child dependency in the website logic, and no Tito order-limit change is required. The earlier suggestion that Test Child W1 had a minimum order limit was incorrect. Tito's own page accepts the same mixed-wave order correctly.

V9 ticket quantity behaviour
----------------------------
- The API provides the starting number available in each price band.
- The on-screen “tickets left” count then updates instantly from the customer’s own selections.
- Each quantity input receives a dynamic HTML max based on the shared Activity allocation, so Adult and Child tickets draw from the same remaining pool.
- When the current-price allocation reaches zero, the next price band is revealed immediately without rebuilding the Tito widget.
- The site does not move quantities or reprice tickets automatically.
- If availability changes concurrently and the customer now has too many current-price tickets selected, Continue is blocked and the warning tells them exactly how many current-price tickets to remove before using the next price.
